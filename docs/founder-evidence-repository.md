# Founder Evidence Repository

Use this repository to store and categorize evidence from founder conversations. This document defines evidence types and review rules. It should not be used to invent proof, inflate signals, or claim validation before patterns repeat.

## Evidence Categories

### Pain Evidence

Evidence that the founder has the underlying problem ThoroughLoop is trying to solve.

Examples:

- Founder describes scattered operating context without being prompted.
- Founder says decisions are hard to revisit later.
- Founder mentions missed follow-ups, unclear owner, or recurring decision drift.
- Founder already has a manual workaround for turning messy notes into action.

### Workflow Evidence

Evidence that the ThoroughLoop loop maps to a real workflow.

Examples:

- Founder can name where diagnosis, memo, action, decision, and review would fit.
- Founder wants to use the loop for a specific workflow, such as sales, feedback, hiring, or investor updates.
- Founder says the review step is valuable, not only the memo.
- Founder asks how the loop would work with a real messy input.

### Language Evidence

Evidence about the words founders naturally use to describe the problem.

Examples:

- Founder uses a phrase that is clearer than the README language.
- Founder describes the pain as decision drift, follow-up decay, scattered notes, or founder context loss.
- Founder rejects language that sounds too broad, too technical, or too productized.

### Objection Evidence

Evidence about what blocks understanding, trust, or usage.

Examples:

- Founder says the output feels too generic.
- Founder thinks it sounds like another note-taking tool.
- Founder asks whether local storage is enough for their workflow.
- Founder wants team collaboration before they would use it repeatedly.

### Validation Evidence

Evidence strong enough to support a future validation claim once repeated.

Examples:

- Multiple founders independently describe the same pain.
- Multiple founders ask to try the demo with their own context.
- Multiple founders identify the same workflow as urgent.
- Multiple founders say the review loop would change how they follow up.

### Non-Evidence

Signals that should not be counted as validation.

Examples:

- Polite compliments.
- General encouragement.
- Comments about the project looking nice.
- Feedback from people outside the target audience that does not map to a founder workflow.
- Feature requests that skip past the current MVP boundary.

## Strong Evidence Examples

- Founder describes the problem unprompted.
- Founder already uses a workaround.
- Founder asks for access.
- Founder requests follow-up.
- Founder asks to paste their own messy context.
- Founder names a recent decision they failed to review.
- Founder says one action is more useful than another broad task list.

## Weak Evidence Examples

- "Interesting idea"
- "Cool project"
- "Nice UI"
- "This could be useful"
- "I like the concept"
- "You should add integrations"
- "Let me know when it has team features"

## Evidence Capture Rules

- Capture exact founder language when available.
- Label paraphrases clearly.
- Keep company names, customer names, metrics, and sensitive details out of public docs.
- Separate pain evidence from product suggestions.
- Separate one-off feedback from recurring patterns.
- Record weak signals and objections with the same discipline as strong signals.
- Do not turn private conversation notes into public claims without review.
- Do not count outreach replies, compliments, or demo views as validation by themselves.

## Evidence Review Process

1. Log each conversation using `docs/validation-log-template.md`.
2. Copy exact wording into `docs/founder-language-bank.md` only when exact wording is available.
3. Add recurring signals to `docs/founder-signal-tracker.md`.
4. Add repeated objections to `docs/founder-objection-library.md`.
5. Update `docs/validation-scorecard.md` after each batch of conversations.
6. Review patterns weekly in `docs/founder-learning-journal.md`.
7. Run a monthly synthesis using `docs/founder-validation-retrospective-template.md`.
8. Only update public positioning after repeated evidence supports the change.
